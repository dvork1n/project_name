## Ответы на контрольные вопросы

### 1. Чем отличается команда git merge от git rebase?

`git merge` объединяет изменения двух веток, сохраняя историю их параллельной разработки. При необходимости создаётся отдельный коммит слияния.

`git rebase` переносит коммиты одной ветки на вершину другой, формируя линейную историю. При этом переносимые коммиты создаются заново и получают новые хеши.

Основное отличие заключается в том, что `merge` сохраняет структуру ветвления, а `rebase` переписывает историю переносимых коммитов.

### 2. Для чего нужен параметр --no-ff при слиянии и что произойдёт без него?

Параметр `--no-ff` принудительно создаёт отдельный merge-коммит, даже если Git может выполнить слияние простым перемещением указателя ветки (fast-forward).

Это позволяет сохранить в истории информацию о том, что изменения разрабатывались в отдельной ветке.

Без параметра `--no-ff` Git по возможности выполнит fast-forward, не создавая отдельного коммита слияния. Если fast-forward невозможен, обычный `git merge` создаст merge-коммит.

### 3. Опишите пошаговый алгоритм действий, если при выполнении git push система сообщает rejected (non-fast-forward).

Ошибка возникает, когда удалённая ветка содержит коммиты, отсутствующие в локальной истории, и обычная отправка изменений не может быть выполнена без предварительной синхронизации.

Алгоритм действий:

1. Проверить состояние репозитория с помощью `git status`.
2. Получить актуальные изменения и интегрировать их в локальную ветку командой `git pull --rebase origin main`.
3. При возникновении конфликтов вручную исправить соответствующие файлы.
4. Добавить исправленные файлы в индекс командой `git add <имя_файла>` и продолжить перенос коммитов через `git rebase --continue`.
5. После успешной синхронизации повторить отправку командой `git push origin main`.

Принудительную отправку через `git push --force` использовать не рекомендуется, поскольку она может перезаписать историю удалённой ветки.

### 4. Что такое индекс (staging area) в Git и зачем нужна команда git add перед git commit, если файл уже отслеживается?

Индекс Git (staging area) — промежуточная область, содержащая подготовленное состояние файлов для следующего коммита.

Команда `git add` переносит текущее содержимое выбранных файлов в индекс. Это позволяет определить, какие именно изменения будут включены в следующий коммит.

Даже если файл уже отслеживается Git, после его редактирования необходимо повторно выполнить `git add`, чтобы подготовить новую версию файла к сохранению.

### 5. Как отменить изменения, которые ещё не были добавлены в индекс (изменения в рабочей директории)?

Для отмены неподготовленных изменений в отслеживаемом файле используется команда:

`git restore имя_файла`

Для отмены неподготовленных изменений во всех отслеживаемых файлах текущего каталога и его подпапок:

`git restore .`

Команды возвращают содержимое файлов к состоянию, сохранённому в индексе. Несохранённые в индексе изменения будут потеряны. Новые неотслеживаемые файлы команда не удаляет.

### 6. Какой командой можно посмотреть, какие файлы были изменены, но ещё не добавлены в коммит?

Для просмотра общего состояния файлов используется команда:

`git status`

Она показывает изменённые, новые и подготовленные к коммиту файлы.

Для просмотра конкретных изменений в отслеживаемых файлах, которые ещё не добавлены в индекс, используется:

`git diff`

Для просмотра изменений, уже подготовленных к следующему коммиту:

`git diff --staged`
